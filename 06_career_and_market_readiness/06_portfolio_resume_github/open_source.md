# Open source: first contributions to funded programmes

| Goal | Time | Level | Back to |
|---|---|---|---|
| Land merged contributions in real projects, build a lasting relationship with one project, and apply to a funded programme (GSoC, Outreachy, LFX, MLH Fellowship) | 10–20 hours to a first merged pull request; 5–8 hours a week to sustain | L2 → L3 | [Portfolio hub](README.md) |

## 1. Why it counts more now

Open-source work is one of the few ways to gain the **tacit knowledge** that AI tools substitute least: reading a large codebase you did not write, following its conventions, getting your code reviewed by strangers, and fixing what they find. The [market map](../01_market_map/README.md#3-entry-level-hiring-what-the-data-shows) recommends exactly this as a response to weaker entry-level hiring. A merged pull request is also verifiable evidence: anyone can open it and read the review.

## 2. Finding a project

Start from tools you already use. You understand their purpose, and you will notice bugs and missing documentation.

**Health checks before you invest time.**

| Signal | Healthy | Warning |
|---|---|---|
| Recent activity | Pull requests merged in the last 30 days | Last merge months ago |
| Response time | Maintainers reply to new issues and pull requests within days to weeks | Many open pull requests with no reply |
| Contributor docs | `CONTRIBUTING.md`, setup instructions, code of conduct | No instructions; "just read the code" |
| Labels | `good first issue`, `help wanted`, `documentation` | No labels, or labels never used |
| CI | Tests run on every pull request | No CI; you cannot know if you broke something |

**Where to look.**

- GitHub search with labels: `is:issue is:open label:"good first issue" language:go`.
- Aggregators: [goodfirstissue.dev](https://goodfirstissue.dev/), [up-for-grabs.net](https://up-for-grabs.net/).
- Foundation contributor guides: [CNCF contributors](https://contribute.cncf.io/), the [Kubernetes contributor guide](https://www.kubernetes.dev/docs/guide/), the [Python developer's guide](https://devguide.python.org/), the [Apache Software Foundation](https://community.apache.org/contributors/).
- India: [FOSS United](https://fossunited.org/) runs community meetups, the IndiaFOSS conference and grants, and is a good place to meet maintainers.

**Contributions that are not code** are real contributions and often the best first step: fixing documentation that misled you, adding a missing test, reproducing a bug report with a minimal example, triaging old issues, improving error messages, translating documentation.

## 3. Your first contribution, step by step

```bash
# 1. Fork on GitHub, then clone your fork and add the original as "upstream"
git clone https://github.com/<you>/<project>.git && cd <project>
git remote add upstream https://github.com/<org>/<project>.git

# 2. Build and run the tests BEFORE changing anything (follow CONTRIBUTING.md)
make test            # or the project's equivalent

# 3. Branch from the latest upstream main
git fetch upstream && git switch -c fix-timezone-parse upstream/main

# 4. Make a small change with a test that fails before and passes after
# 5. Commit with sign-off if the project uses a Developer Certificate of Origin (DCO)
git commit -s -m "Fix timezone offset parsing for +05:30 inputs (#1234)"

# 6. Push and open a pull request using the project's template
git push origin fix-timezone-parse

# 7. After review: make changes, then update the branch the way the project asks
git fetch upstream && git rebase upstream/main && git push --force-with-lease
```

**Legal sign-offs.** Many Linux Foundation projects require a DCO sign-off (`-s` adds a `Signed-off-by` line). Some organisations instead require a Contributor License Agreement (CLA), signed once online before your first pull request can be merged. Read the project's rules before you start.

**Etiquette.**

1. **Comment before you start** on an issue: say what you plan to do in two lines. Do not post only "Can I work on this?", and do not claim several issues at once.
2. **Small pull requests.** One fix, with a test, and a description that links the issue and explains how you verified it.
3. **Respond to review within a few days**, and thank reviewers. Review is free mentoring.
4. **Do not ping maintainers repeatedly.** Most are volunteers. One polite follow-up after a week or two is enough.
5. **Follow the code of conduct** in issues, chat and reviews.

## 4. AI-generated contributions

Maintainers receive a growing number of low-quality AI-generated pull requests and bug reports, and some projects now restrict them:

- **Gentoo** adopted a policy on 14 April 2024 forbidding contributions created with the assistance of natural-language-processing AI tools ([Gentoo Council AI policy](https://wiki.gentoo.org/wiki/Project:Council/AI_policy)).
- **NetBSD** treats code generated by large language models as presumed tainted, not to be committed without prior written approval from its core team ([NetBSD commit guidelines](https://www.netbsd.org/developers/commit-guidelines.html)).
- The maintainer of **curl** described bogus AI-generated security reports that waste maintainer time ([Daniel Stenberg, 2 Jan 2024](https://daniel.haxx.se/blog/2024/01/02/the-i-in-llm-stands-for-intelligence/)).

Rules for using AI tools in open source:

1. **Read the project's policy** (often in `CONTRIBUTING.md`). If it forbids AI-generated content, do not use it.
2. **Understand every line** you submit. You must be able to answer any review question without asking an AI tool.
3. **Disclose** meaningful AI assistance in the pull request description where the project allows it.
4. **Never submit an AI-generated bug or security report** that you have not reproduced yourself. Follow the project's security policy (`SECURITY.md`) for anything security-related, and report privately.
5. **Use AI to understand, not to submit:** asking a tool to explain an unfamiliar module or a failing test is a good use; pasting its patch unchanged is not.

## 5. Funded programmes (checked October 2026)

These programmes pay contributors to work with a mentor for a fixed period. They are competitive; your prior contributions to the organisation are usually the deciding factor.

May 2027 cohort: applications usually open in early February |

**Other programmes to check each year** (status and dates for 2026 not verified here): Hacktoberfest (held each October since 2014), Season of KDE, Summer of Bitcoin, GirlScript Summer of Code, and India's Code for GovTech (C4GT) mentoring programme. ## 6. Writing a proposal (GSoC, LFX, Outreachy)

```markdown
# <Project idea title> · <Organisation>

## About me
Name, university and year, time zone, email, GitHub. One paragraph on relevant experience.

## Prior contributions to this organisation
- #1234 Fix timezone offset parsing (merged)
- #1301 Tests for config loading (merged)
- #1350 Draft: prototype of <feature> (under review)

## Problem
What is missing today and who it affects. Link the issue or idea page.

## Proposed solution
Design with one diagram. Interfaces you will add or change. How you will test it.
Alternatives you considered and why you did not choose them.

## Deliverables
1. ... (each one measurable: "merged", "documented", "benchmarked against X")

## Timeline (week by week)
| Week | Work | Checkpoint |
|---|---|---|
| Community bonding | Read code paths A and B; agree design with mentor | Design doc approved |
| 1–2 | ... | PR #1 opened |

## Availability
Hours per week, exams, holidays, any other commitments.
```

What makes proposals succeed:

1. **Contribute first.** Two or three merged pull requests in the organisation before the application window are the strongest signal you can give.
2. **Talk to mentors early** on the project's public channels. Ask specific questions that show you read the code.
3. **Scope realistically.** A smaller project you finish beats an ambitious one you abandon.
4. **Write it yourself.** Mentors read many proposals; generic AI-written ones are easy to recognise and suggest you will not do the work.

## 7. A 12-month plan

| Month | Goal |
|---|---|
| 1 | Pick three candidate projects using the health checks. Build each from source; run the tests |
| 2 | First contribution (documentation or a test) to one of them |
| 3 | First code fix with a test |
| 4–5 | Two more merged pull requests in the same project; join its chat and meetings |
| 6 | Review other contributors' pull requests (comment helpfully, even if you cannot approve) |
| 7–8 | A medium-size feature or bug, agreed with a maintainer first |
| 9 | Programme application (GSoC in March, Outreachy May cohort in February, LFX by term) |
| 10–12 | Programme work, or keep contributing; aim to be listed as a reviewer or code owner for one area |

## 8. On your resume and profile

- Name the project, the number of merged pull requests and one specific contribution with its link.
- "Contributor to Kubernetes" with one documentation typo fix will be checked and will hurt. Be precise: "1 merged documentation fix in kubernetes/website".
- Ask a maintainer who reviewed your work for a short recommendation if you contributed substantially.

## 9. Practice

1. Apply the health-check table to five projects you use. Write down which three you would choose and why.
2. Reproduce one open bug in a project of your choice with a minimal example and post it on the issue.
3. Draft the "Prior contributions" and "Timeline" sections of a proposal for a real idea on a GSoC organisation's ideas page.
